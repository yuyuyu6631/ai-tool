## 2025-02-09 - [发现性能瓶颈]
**经验：** 后端服务 `apps/api/app/services/catalog_service.py` 中的 `get_home_catalog` 和其他方法在调用 `_load_summaries` 时频繁执行数据库查询，并且可能会返回数千个工具对象，之后在方法内仅保留切片，存在冗余的 N+1 查询甚至大量无效内存使用和查询负担。另外在获取列表和切片时可进行优化。不过由于要求是做一些有明显效果但不引入风险的优化，可以在 `get_home_catalog` 观察 `_sort_tools(all_tools, ...)` ，每次都会全排序所有 tools 得到 `hot_tools` 和 `latest_tools`，然后再遍历工具分类做同样的排序。这是一个非常耗时的全量排序+切片的操作，每次进入主页都会全量扫描加载并在内存里做数十次全量数组排序。这部分值得优化并缓存。
**行动：** 寻找能够安全应用缓存的方法，比如像 `list_categories` 或 `list_scenarios` 等接口一样，将组装好的首页面数据进行 Redis 缓存。
## 2026-05-08 - [首页目录全量数组排序和分类遍历的缓存优化]
**经验：** 后端服务中的 `get_home_catalog` 对于首页的各个板块都要做全量的排序，当后端返回包含数百甚至数千的工具时，在内存里反复排序极其消耗 CPU 并增加了 GC 压力。由于此类主页结构不常更新且具有高频请求特性，应充分利用现有的 Redis 缓存机制对全序列化的请求做缓存。
**行动：** 添加 Redis 缓存逻辑将 `get_home_catalog` 的返回值缓存 5 分钟，避免 N+1 甚至更频繁的查询。
