# 星点评生产部署运行手册

本手册记录 2026-05-07 当前确认可用的生产部署方式，目标是让后续值班、发布和排障能按统一口径执行，避免再次混淆服务器、入口和启动方式。

配套背景文档：

- 入口与公网排障经验见 [16-公网部署与上线排障经验.md](./16-公网部署与上线排障经验.md)
- 当前代码与产品约束先看 [00-最终效果约束.md](./00-最终效果约束.md)

## 1. 当前拓扑

当前线上分成两层：

- 内网运行机：`192.168.8.200`
- 公网入口：`http://changsha.01view.ydns.eu:12318/xingdp/`

当前验证通过的访问关系：

- `http://192.168.8.200:3000/` -> 星点评 Web
- `http://192.168.8.200:8000/health/ready` -> 星点评 API
- `http://changsha.01view.ydns.eu:12318/xingdp/` -> 公网代理后的星点评 Web
- `http://changsha.01view.ydns.eu:12318/xingdp/api/health` -> 公网代理后的星点评 API

重要说明：

- `52.82.11.16` 不是当前星点评有效部署机，不要再把它当成生产发布目标。
- 当前公网代理会把 `/xingdp` 前缀剥掉后再转发到 `192.168.8.200:3000`。
- 因为有这层剥离，Web 侧必须同时兼容 `/api/*` 和 `/xingdp/api/*` 两种入口。

## 2. 正确登录方式

当前确认可用的是密码登录：

- 主机：`192.168.8.200`
- 端口：`22`
- 用户：`agent`
- 认证方式：密码

密码不写入仓库。应从受控渠道获取，不要把密码、私钥、截图直接提交到代码库。

登录成功后工作目录应为：

```text
/home/agent/xingdianping
```

## 3. 当前运行方式

当前不是 Docker，也不是 systemd service，而是 `agent` 用户下的 rootless Podman。

GitHub Actions 当前不作为生产发布入口。仓库里的 Actions 只允许手动构建镜像用于验证，不负责 SSH 上线；生产发布应直接登录 `192.168.8.200` 后执行本手册中的 Podman 脚本。

当前运行容器：

- `xdp-mysql`
- `xdp-redis`
- `xdp-api`
- `xdp-web`

当前确认可用的启动模式：

- 四个容器统一使用 `podman --network host`
- 不再依赖 rootless Podman 的 `-p 3000:3000`、`-p 8000:8000` 端口映射

原因：

- 这台机此前 `podman -p` 显示有映射，但宿主机 `192.168.8.200:3000` 和 `:8000` 实际拒绝连接
- 改为 `--network host` 后，Web/API/MySQL/Redis 可以稳定直接监听宿主机端口

## 4. 当前关键文件

部署目录中的关键文件：

- `/home/agent/xingdianping/.env.runtime`
- `/home/agent/xingdianping/Containerfile.api.prod`
- `/home/agent/xingdianping/Containerfile.web.prod`
- `/home/agent/xingdianping/deploy_podman_prod.sh`
- `/home/agent/xingdianping/start_podman_prod.sh`
- `/home/agent/xingdianping/xingdp_proxy_server.cjs`

当前特别关键的一点：

- `xingdp_proxy_server.cjs` 必须同时代理 `/api/*` 和 `/xingdp/api/*`
- 否则公网入口 `http://changsha.01view.ydns.eu:12318/xingdp/api/health` 会返回 `404`

这些文件现在应随仓库版本管理，服务器部署目录通过 `git pull --ff-only origin main` 同步，不应只依赖服务器上的临时手写脚本。

## 5. 启动前检查

上线前先做这几步：

```bash
cd /home/agent/xingdianping
podman ps -a --format '{{.Names}} {{.Status}}'
ps -ef | grep -E 'deploy_podman|podman build|xdp-' | grep -v grep || true
df -h /home / || true
podman system df || true
```

重点看：

- 是否有残留 `podman build`
- 是否有历史 `xdp-*` 容器处于异常状态
- 磁盘是否不足

如果构建空间紧张，可执行：

```bash
podman image prune -f
podman builder prune -af
```

执行前确认没有正在依赖的构建过程。

## 6. 标准重启流程

当前推荐的重启顺序如下：

1. 停旧容器
2. 启 MySQL、Redis
3. 等 MySQL ready
4. 启 API
5. 等 API ready
6. 启 Web
7. 做本机和外部验收

标准发布命令：

```bash
cd /home/agent/xingdianping
git fetch origin main
git checkout main
git pull --ff-only origin main
chmod +x ./deploy_podman_prod.sh ./start_podman_prod.sh
./deploy_podman_prod.sh
```

当前可用命令模板：

```bash
cd /home/agent/xingdianping

podman rm -f xdp-web xdp-api xdp-redis xdp-mysql 2>/dev/null || true
podman volume exists xdp-mysql-data || podman volume create xdp-mysql-data >/dev/null

podman run -d --replace --name xdp-mysql --network host \
  -e MYSQL_ROOT_PASSWORD=root \
  -e MYSQL_DATABASE=xingdianping \
  -e MYSQL_USER=xingdianping \
  -e MYSQL_PASSWORD=xingdianping \
  -v xdp-mysql-data:/var/lib/mysql \
  docker.m.daocloud.io/library/mysql:8.4

podman run -d --replace --name xdp-redis --network host \
  docker.m.daocloud.io/library/redis:7.4-alpine

for i in {1..120}; do
  if podman exec xdp-mysql mysqladmin ping -h 127.0.0.1 -uroot -proot --silent >/dev/null 2>&1; then
    break
  fi
  sleep 2
done

podman run -d --replace --name xdp-api --network host \
  --env-file /home/agent/xingdianping/.env.runtime \
  -e DATABASE_URL=mysql+pymysql://xingdianping:xingdianping@127.0.0.1:3306/xingdianping \
  -e REDIS_URL=redis://127.0.0.1:6379/0 \
  xdp-api:latest \
  sh -c 'alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port 8000'

podman run -d --replace --name xdp-web --network host \
  --env-file /home/agent/xingdianping/.env.runtime \
  -e NEXT_PUBLIC_API_BASE_URL=http://192.168.8.200:8000 \
  -e PORT=3000 \
  -e HOSTNAME=0.0.0.0 \
  xdp-web:latest
```

## 7. Web 构建要点

当前 Web 镜像不是直接暴露 Next，而是：

- 容器内 Next 跑在 `127.0.0.1:3001`
- `xingdp_proxy_server.cjs` 监听 `3000`
- 代理静态资源、页面请求和 API 请求

当前 Web 镜像构建后的启动命令逻辑是：

```text
PORT=3001 HOSTNAME=127.0.0.1 node apps/web/.next/standalone/apps/web/server.js
node /workspace/xingdp_proxy_server.cjs
```

因此排障时不要只看 Next 是否启动，还要看代理脚本是否把：

- `/`
- `/xingdp/`
- `/api/*`
- `/xingdp/api/*`

都转发正确。

## 8. API 环境要求

当前 API 依赖：

- MySQL：`127.0.0.1:3306`
- Redis：`127.0.0.1:6379`

`.env.runtime` 中至少要保证：

```env
ENVIRONMENT=production
DATABASE_URL=mysql+pymysql://xingdianping:xingdianping@127.0.0.1:3306/xingdianping
REDIS_URL=redis://127.0.0.1:6379/0
CORS_ALLOWED_ORIGINS=http://192.168.8.200:3000,http://localhost:3000,http://127.0.0.1:3000
NEXT_PUBLIC_API_BASE_URL=http://192.168.8.200:8000
AUTH_SECRET_KEY=...
```

敏感配置如密码、密钥只保存在服务器 `.env.runtime`，不要回写到仓库。

## 10. 常见故障与判断

### 1. `podman ps` 显示端口映射正常，但浏览器访问拒绝连接

优先判断是否又回到了 rootless Podman 的 `-p` 模式。

修复方式：

- 改回 `--network host`
- 不要把这台机的稳定性赌在 rootless `-p 3000:3000` 上

### 2. 外网首页正常，但 `/xingdp/api/health` 是 `404`

这通常不是 API 挂了，而是 Web 代理脚本没同时兼容：

- `/api/*`
- `/xingdp/api/*`

原因是公网代理可能已经提前剥离了 `/xingdp`。

### 3. Web 起来了，但页面里请求内网 IP

优先检查：

- `NEXT_PUBLIC_API_BASE_URL`
- `apps/web/src/app/lib/api-base.ts`
- 公网场景下是否应使用同源 `/xingdp/api/*`

### 4. MySQL、Redis 启动后很快退出

先看：

```bash
podman logs xdp-mysql --tail 100
podman logs xdp-redis --tail 100
```

再看是否是端口冲突、磁盘满、数据目录权限问题。

### 5. 明明容器起了，但公网不通

分三段判断：

1. `127.0.0.1` 是否通
2. `192.168.8.200` 是否通
3. `changsha.01view.ydns.eu:12318/xingdp/` 是否通

这样能快速分清是应用问题、主机监听问题，还是公网代理问题。

## 12. 后续调度建议

以后涉及“线上恢复 / 公网修复 / 紧急发版”时，执行顺序建议固定为：

1. 先确认目标机器是不是 `192.168.8.200`
2. 先确认登录用户是不是 `agent`
3. 先确认 `/home/agent/xingdianping` 是否存在
4. 先检查 `podman ps -a`
5. 再决定是只重启 `xdp-web`，还是重启整套四容器
6. 每次改动后都按“本机 -> 局域网 -> 公网”三段验收

不要跳过这几步，否则很容易把时间浪费在错误服务器、错误入口或错误网络层上。
